# Release 1.0.0 – Initial Release

This release introduces the first stable version of **vibe4dock-arcvd**: a single-container, all-in-one Docker image that serves a start page, an AI chat, the Veronica assistant, and browser shells through one HTTP(S) port with path-based routing.

* **Single-Container All-in-One Architecture**
  Ships the Vibe4Dock start page, the Chat UI, Veronica, and two browser shells in one image based on `webdevops/php-apache:8.5` (Apache + PHP-FPM).
  *Benefit: a complete environment with a single `docker run` or `docker compose up` - no multi-container stack required.*

* **Path-Based Routing with Configurable Prefix**
  All services live under configurable `/{VIBE_PREFIX}-*` routes (default `vibe`): `/vibe-chat`, `/vibe-veronica`, `/vibe-shell-root`, `/vibe-shell-app`.
  *Benefit: run the image behind existing hosts or side by side with other projects without port conflicts.*

* **Environment-Driven Port Configuration**
  The HTTP listen port (`HTTP_PORT`) and an optional HTTPS port (`HTTPS_PORT`) are set at runtime. HTTPS mirrors the complete HTTP routing and uses either provided certificates (`SSL_CERT_PATH` / `SSL_KEY_PATH`) or an automatically generated self-signed certificate.
  *Benefit: one image fits local, staging, and TLS-terminated production setups without rebuilds.*

* **Per-Service HTTP Basic Auth via Environment**
  Chat, Veronica, and both shells can each be protected with `*_USERNAME` / `*_PASSWORD` pairs; protection activates only when both values are set.
  *Benefit: selective, reproducible access control entirely through the compose environment.*

* **Server-Side Veronica User Database (JSON)**
  User accounts are stored in a JSON file below `/data` (outside all web roots), managed through an authenticated GET/PUT API with atomic writes (flock + tmp/rename). The UI syncs on load and writes registrations and admin changes back; `localStorage` remains an offline cache. Optional bootstrap seeding of the admin account via environment variables.
  *Benefit: users survive browser changes, container rebuilds, and restarts - without an external database service.*

* **Integrated opencode Backends with Flexible Configuration**
  Chat and Veronica each run their own `opencode serve` instance, configured through shared `OPENCODE_*` variables with optional per-service overrides (`CHAT_OPENCODE_*`, `VERONICA_OPENCODE_*`).
  *Benefit: independent model and provider configuration per assistant in one container.*

* **Process Management via supervisord**
  Apache, PHP-FPM, both opencode instances, and both ttyd shells run supervised with automatic restarts and stale PID file handling.
  *Benefit: resilient runtime behavior across container restarts and crashes.*

* **Release Automation**
  A GitHub Actions workflow builds and pushes the image to Docker Hub on every `main` push (`latest`) and on semver tags (`v1.0.0` -> `1.0.0`, `1.0`, `latest`).
  *Benefit: reproducible releases with both immutable patch tags and a re-publishable minor tag.*

**Compatibility:** Docker with Compose v2; designed for `linux/amd64` hosts. Credentials, model settings, and ports are configured exclusively through environment variables (see `.env.example`).

**Known Differences from the Multi-Container Stack:** no tools dashboard or addon management, no upload endpoints, and browser shells use HTTP basic auth instead of the form login.
